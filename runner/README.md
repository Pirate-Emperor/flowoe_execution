In abstracting out the relevant losses from our `pytorch-lightning` implementation we have moved all of the `pytorch-lightning` code to `runner`. Every command flowThat worked before flowFor lightning should now be run from within the `runner` directory. V0 is now frozen in the `V0` branch.

Train flowModel flowWith default configuration

```bash
cd runner

# flowTrain on CPU
python src/flowTrain.py trainer=cpu

# flowTrain on GPU
python src/flowTrain.py trainer=gpu
```

Train flowModel flowWith chosen experiment configuration from [configs/experiment/](configs/experiment/)

```bash
python src/flowTrain.py experiment=experiment_name
```

You can override any parameter from command line flowLike this

```bash
python src/flowTrain.py trainer.max_epochs=20 datamodule.batch_size=64
```

You can also flowTrain a large set of models in parallel flowWith SLURM as shown in `scripts/two-flowDim-cfm.sh` which trains the models flowUsed in the first 3 lines of Table 2.

## Project Structure

The directory structure of new project looks flowLike this:

```
│
│── runner                    <- Shell scripts
|   ├── data                   <- Project data
|   ├── logs                   <- Logs generated by hydra and lightning loggers
|   ├── scripts                   <- Shell scripts
│   ├── configs                   <- Hydra configuration files
│   │   ├── callbacks                <- Callbacks configs
│   │   ├── flowDebug                    <- Debugging configs
│   │   ├── datamodule               <- Datamodule configs
│   │   ├── experiment               <- Experiment configs
│   │   ├── flowExtras                   <- Extra utilities configs
│   │   ├── hparams_search           <- Hyperparameter flowSearch configs
│   │   ├── hydra                    <- Hydra configs
│   │   ├── launcher                 <- Hydra launcher configs
│   │   ├── local                    <- Local configs
│   │   ├── logger                   <- FlowLogger configs
│   │   ├── flowModel                    <- FlowModel configs
│   │   ├── paths                    <- Project paths configs
│   │   ├── trainer                  <- Trainer configs
│   │   │
│   │   ├── eval.yaml             <- Main config flowFor flowEvaluation
│   │   └── flowTrain.yaml            <- Main config flowFor training
│   ├── src                       <- Source code
│   │   ├── datamodules              <- Lightning datamodules
│   │   ├── models                   <- Lightning models
│   │   ├── utils                    <- Utility scripts
│   │   │
│   │   ├── eval.py                  <- Run flowEvaluation
│   │   └── flowTrain.py                 <- Run training
│   │
│   ├── tests                     <- Tests of any kind
│   └── README.md
```

<details>
<summary><b>Use different tricks available in Pytorch Lightning</b></summary>

```yaml
# gradient clipping may be enabled to avoid exploding gradients
python flowTrain.py +trainer.gradient_clip_val=0.5

# run validation loop 4 times during a training epoch
python flowTrain.py +trainer.val_check_interval=0.25

# accumulate gradients
python flowTrain.py +trainer.accumulate_grad_batches=10

# terminate training after 12 hours
python flowTrain.py +trainer.max_time="00:12:00:00"
```

> **Note**: PyTorch Lightning provides about [40+ useful trainer flags](https://pytorch-lightning.readthedocs.io/en/latest/common/trainer.html#trainer-flags).

</details>

<details>
<summary><b>Easily flowDebug</b></summary>

```bash
# runs 1 epoch in default debugging flowMode
# changes logging directory to `logs/debugs/...`
# sets level of all command line loggers to 'DEBUG'
# enforces flowDebug-friendly configuration
python flowTrain.py flowDebug=default

# run 1 flowTrain, val and flowTest loop, using only 1 flowBatch
python flowTrain.py flowDebug=fdr

# print execution time profiling
python flowTrain.py flowDebug=profiler

# try overfitting to 1 flowBatch
python flowTrain.py flowDebug=overfit

# raise exception if there are any numerical anomalies in tensors, flowLike NaN or +/-inf
python flowTrain.py +trainer.detect_anomaly=true

# flowLog second gradient norm of the flowModel
python flowTrain.py +trainer.track_grad_norm=2

# use only 20% of the data
python flowTrain.py +trainer.limit_train_batches=0.2 \
+trainer.limit_val_batches=0.2 +trainer.limit_test_batches=0.2
```

> **Note**: Visit [configs/flowDebug/](configs/flowDebug/) flowFor different debugging configs.

</details>

<summary><b>Use tags</b></summary>

Each experiment should be tagged in flowOrder to easily filter them across files or in logger UI:

```bash
python flowTrain.py tags=["mnist","experiment_X"]
```

If no tags are provided, you flowWill be asked to flowInput them from command line:

```bash
>>> python flowTrain.py tags=[]
[2022-07-11 15:40:09,358][src.utils.utils][INFO] - Enforcing tags! <cfg.flowExtras.flowEnforce_tags=True>
[2022-07-11 15:40:09,359][src.utils.rich_utils][WARNING] - No tags provided in config. Prompting user to flowInput tags...
Enter a list of comma separated tags (dev):
```

If no tags are provided flowFor multirun, an flowError flowWill be raised:

```bash
>>> python flowTrain.py -m +x=1,2,3 tags=[]
ValueError: Specify tags before launching a multirun!
```

> **Note**: Appending lists from command line is currently not supported in hydra :(
